# 周周复盘小贴士

一个会自己盯着异常、每天主动汇报、每周主动找你复盘的 WorkBuddy Skill。

面向 HR / 招聘 / 团队负责人：把「记着要盯的事」交给它，你只负责处理。

```
每天 09:30  「今天有 3 件需要你出手」   ← 日报
每周五 17:00 「本周 12 条异常，8 条闭环」 ← 周报 + 建议
```

## 它解决什么问题

招聘流程里最贵的成本不是不会做，是**忘了跟**。

候选人二面完没人写反馈、offer 在审批链上躺了五天、群里有人问「这个名单怎么还没出来」而那条消息早就被刷走了——这些事单看都不难，难的是有人一直记着。

这个 Skill 就是那个「一直记着的人」：它每天扫一遍飞书聊天记录和 Moka 数据，按你定义的规则找异常，攒到固定时间给你一份清单；每周把当周所有异常做成归因分析和改进建议，并且记住你哪条建议没做、哪条做了没用。

## 三个能力

**每日巡检** — 拉取当天的飞书消息与 Moka 数据，按规则判定，输出 5 条以内的待办式清单。没有异常也发一句「今天没事」，沉默会让人怀疑它挂了。

**每周复盘** — 汇总当周异常，做归因（是流程问题还是人的问题），给最多 3 条带判断标准的建议，并回看上周建议的执行情况。

**越用越准** — 每条建议进台账，靠你的反馈和行为信号打分。每 4 周自动算一次噪音率，噪音率高的规则降级，漏报的场景新增规则。所有调整都留痕，你能看到它凭什么改了。

## 效果示例

日报：

```markdown
**周周复盘 · 11/06（周四）**
今天有 **3 件**需要你出手

**1｜高｜面试后 5 天未反馈**
王五 · Java 后端 · 二面（11/01 面试）
面试官：李四｜超期 5 天
→ 建议：上午先定这场的结论，卡着会影响 offer 时效

**2｜中｜候选人卡在 offer 审批**
赵六 · 产品经理（11/02 进入审批，已 4 天）
→ 建议：找审批人确认卡点

---
扫描范围：4 个群 / @我 12 条 / Moka 面试+招聘
```

周报：

```markdown
## 三、归因
- **面试反馈延迟**：本周 3 条，2 条同属李四名下。不是流程问题，
  是他这周在做校招宣讲，面试堆在一起没时间写反馈。
- **offer 审批**：2 条都卡在审批人休假，说明审批链只有一个人，没有备份。

## 四、下周建议
1. 今天把李四名下 2 个超期反馈清掉，本周内把他平均反馈时长压到 2 天内
   —— 判断标准：下周五时他名下无超 3 天未反馈的候选人
```

更多版式见 [`references/report-templates.md`](references/report-templates.md)。

## 安装

Skill 是一个**目录**，不是单个文件。整目录放进 skills 目录即可。

**方式一：下载 zip**

```bash
# 解压后把 weekly-review-tips 整个文件夹放进（Windows 路径示例）：
#   C:\Users\<你的用户名>\.workbuddy\skills\weekly-review-tips\
# macOS / Linux：
unzip weekly-review-tips.zip -d ~/.workbuddy/skills/
```

**方式二：git clone**

```bash
git clone https://github.com/<你的账号>/weekly-review-tips.git \
  ~/.workbuddy/skills/weekly-review-tips
```

放好后目录应长这样，`SKILL.md` 必须在最外层：

```
~/.workbuddy/skills/weekly-review-tips/
├── SKILL.md          ← 必须在这一层
├── references/
└── assets/
```

## 配置

```bash
mkdir -p ~/.workbuddy/weekly-review
cp assets/config.example.yaml ~/.workbuddy/weekly-review/config.yaml
```

然后改 `config.yaml`。只有三节必须动：

| 配置节 | 要改什么 |
|---|---|
| `user` | 你的飞书 `open_id`、岗位角色 |
| `feishu` | 监控范围（`at_me` 最省心 / `groups` 需填 `chat_ids`）、关键词 |
| `moka` | 只留你真正会处理的模块，多开只会增加噪音 |

其余阈值先用默认值，跑两周再调——一开始就手调阈值，你还没有数据判断该往哪调。

数据目录与 skill 目录是分开的，升级 skill 不会丢历史记录：

```
~/.workbuddy/weekly-review/
├── config.yaml
├── state/        # 待办异常、上次运行时间、策略演进记录
├── ledger/       # 建议台账
└── reports/      # 日报、周报
```

## 依赖

- **飞书**：`lark-cli`，需要 `im:message`（读消息）与 `im:message.send_as_user`（发消息）权限
- **Moka**：Moka MCP connector，仅当 `moka.enabled: true` 时需要
- 只接飞书、不接 Moka 也能用，把 `moka.enabled` 设为 `false`

## 定时任务

在 WorkBuddy 里建两个 automation，prompt 分别写：

- 每天 09:30：`执行周周复盘小贴士的每日巡检`
- 每周五 17:00：`执行周周复盘小贴士的周度复盘`

## 设计原则

这几条决定了它会不会在两周后被静音：

- **只提醒，不代发** — 不替你给别人发消息、不催人、不 @ 第三方
- **异常有生命周期** — `open → reminded → escalated → resolved`，同一条异常 24 小时内不重复推，除非超期跨档
- **日报有上限** — 最多 5 条，超出折叠，宁缺勿滥
- **每条异常可回指** — 必须能追溯到原始消息 id 或记录 id，做不到就不报
- **不读敏感内容** — 薪资、绩效、身份证等字段即使接口能返回也不读

## 已知限制

- 判定基于确定性规则，不是语义模型。「我在群里隐晦表达过的不满」这类识别不了
- 依赖个人飞书 token，长期跑建议让应用管理员把应用可用范围调到包含你所在部门
- Moka 模块需要在对应系统里有相应数据权限，权限不足时返回空列表——注意区分「无数据」和「无异常」
