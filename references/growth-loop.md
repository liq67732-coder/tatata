# 成长循环

一个只会每天报同样的东西的助手，两周后就会被静音。让建议变准的关键不是更强的模型，而是**记得住自己说过什么、有没有用**。

三条链路：记账 → 校准 → 阶段复盘。

---

## 一、建议台账

文件：`~/.workbuddy/weekly-review/ledger/suggestions.csv`

```csv
id,date,week,type,advice,target,deadline,success_criteria,outcome,feedback_at,note
s-20261108-1,2026-11-08,2026-W45,interview_feedback,清李四名下2个超期反馈,李四,2026-11-12,周五时无超3天未反馈候选人,worked,2026-11-15,宣讲周堆压导致
s-20261108-2,2026-11-08,2026-W45,approval_pending,给offer审批加备份审批人,审批链,2026-11-20,下次休假不滞留,failed,2026-11-22,人事流程要走总部
```

字段说明：

| 字段 | 取值 | 用途 |
|---|---|---|
| `type` | 对应异常规则 id | 统计哪类异常的建议最有效 |
| `advice` | 一句话动作 | 复盘时看是否重复说过同一句 |
| `success_criteria` | 可判断的标准 | 没有它就无法判定 outcome |
| `outcome` | `pending` / `worked` / `failed` / `ignored` | 校准的核心输入 |
| `note` | 失败原因 | 换思路的依据 |

**判定规则**（关键，别含糊）：

- `worked` — 对应异常在 deadline 后 2 周内没有再出现，或用户明确说有效
- `failed` — 执行了但异常照旧出现
- `ignored` — 用户没做（不是建议不好，是他不想做或顾不上）
- `pending` — 未到 deadline

`ignored` 和 `failed` 要严格区分：前者说明建议「不合适」，后者说明建议「不正确」。混在一起会把结论带偏。

## 二、反馈采集

用户不会主动填表，所以只能在他自然会回复的地方接：

1. 周报发出后加一句 `回复「有用 / 没用 / 没做」我来记账（只针对第 1 条）` —— 一次只问一条，问多了没人回
2. 用户回复后更新对应 `outcome` 和 `feedback_at`
3. 用户连续两周不回复 → 停止追问，改用行为判断：对应异常在后续两周是否复现
4. 也可以在日报里对高优先级条目加一个表情反应位（👌 表示已处理），有 `reactions` 数据时可直接读

### 行为信号（比口头反馈更可信）

- 某条异常报了之后，对应的 群消息 / Moka 记录在 24 小时内发生了变化 → 强信号：这条报得有用
- 某条异常连续报到第 3 次仍无任何动作 → 强信号：这条对用户不重要，降级或删规则
- 用户主动说「以后别报这个」→ 立即从日报剔除，移入周报观察区

## 三、阈值自校准（每 4 周）

按规则逐条计算三个指标：

```
命中数     = 该规则近 4 周产生的异常条目数
采用数     = outcome ∈ {worked} 的条目数 + 有行为信号的条目数
噪音率     = 1 - 采用数 / 命中数
```

调整决策表：

| 情况 | 判定 | 动作 |
|---|---|---|
| 噪音率 > 60% 且命中 ≥ 8 | 明显过报 | 阈值 ×1.5，或直接移出日报、只进周报 |
| 噪音率 40%-60% | 边缘 | 阈值 +1 天，观察一个周期 |
| 噪音率 < 20% 且用户曾手动补报同类 | 漏报 | 阈值 ×0.7，或新增细分规则 |
| 某规则 4 周命中 0 条 | 可能失效 | 检查数据源是否取到；数据正常则删除规则 |
| 命中 0 但用户抱怨过漏报 | 规则写错了 | 重写判定条件，不要只调阈值 |

**边界**：单次调整幅度不超过 50%，避免一周之内从「太吵」跳到「全漏」。每次只动 2-3 条规则，动太多无法归因是哪条改对了。

每次调整写一行到 `state/strategy.md`：

```
2026-11-15 | R3 职位无新简历 | 7天 → 只进周报 | 4周命中12条，处理1条，噪音率92%
2026-11-15 | R2 面试反馈 | 2天 → 3天 | 4周命中14条，处理7条，噪音率50%，边缘区
```

## 四、建议质量迭代

阈值解决「报不报」，建议解决「报了有没有用」。每 4 周看三件事：

**1. 建议是不是重复**
同一个 `type` 下连续出现语义相同的 `advice`（比如连着三周都是「催一下 XX」），说明前两次没解决根因。这时不要换措辞，要**换层次**：从「催这个人」上升到「这个环节为什么总是他卡」。

**2. 建议的颗粒度对不对**
统计 `worked` 的建议有个共同特征——都能在一周内做完、都指向具体的人和事。`ignored` 的建议通常是「改流程」「建机制」这类需要跨部门推动的事。结论：**多给小事，大改留给用户自己决定**。

**3. 建议有没有超出权限**
用户是 HR，建议「让技术总监改面试排期」就不合适。判断标准：这条建议用户能不能自己动手完成，不需要说服别人。

## 五、阶段复盘（每 4 周）

输出一份 200 字以内的回顾，固定三问（模板见 `report-templates.md`）：

1. 这 4 周报的准不准？（噪音率、采用率）
2. 建议有没有被执行？（执行率，按类型拆）
3. 下一阶段盯什么、不盯什么？（要改的规则清单）

改 `config.yaml` 之前必须把这三条结论发给用户确认。**不要自己改完再通知**——这个助手的价值建立在「用户信任它的判断」上，自作主张改规则会直接破坏这个信任。

## 六、长期记忆

除了台账，还需要一份「用户偏好」记录，写在 `state/strategy.md` 顶部：

```markdown
## 用户偏好（持续更新）
- 不喜欢早上 8 点前收到消息
- 讨厌「请及时处理」这类空话，要具体动作
- 对考勤类异常只关心缺卡，不关心迟到
- 周报希望周一早上看到，而不是周五
- 候选人姓名允许出现在私聊报告，但周报对外转发时只写姓氏
```

每次从对话里发现新的偏好就追加一行。这份偏好比任何规则都重要——它决定了输出「像不像他想要的东西」。
