# 异常规则库

规则由 `config.yaml` 的 `rules` 节驱动。下面给出九条默认规则的判定逻辑和推荐阈值，首次配置时按用户的实际场景裁剪——**只留用户真的会去处理的规则**，留太多等于没有。

## 阈值档位

`config.tolerance` 决定所有规则的阈值系数，避免逐条手调：

| 档位 | 系数 | 效果 | 适用 |
|---|---|---|---|
| `strict` | ×0.6 | 更容易报，宁可多打扰 | 事情真的很容易烂在手里 |
| `moderate` | ×1.0 | 默认，超期 1-2 天才报 | 大多数岗位 |
| `loose` | ×1.5 | 只报明显要出问题的 | 团队执行力强、讨厌噪音 |

下表的「默认天数」均为 `moderate` 档，实际阈值 = 默认天数 × 系数，向上取整。

---

## R1 候选人在阶段停留过久 `candidate_stuck`

- **数据**：`list_pipeline_candidates`（含候选人当前阶段、进入该阶段时间）
- **条件**：`当前时间 - 进入当前阶段时间 > 阈值`，且候选人未处于终态（已入职 / 已淘汰 / 已放弃）
- **默认**：初筛 3 天、面试中 5 天、offer 审批 3 天
- **严重度**：面试中 > 7 天 → high；其余 medium
- **反噪音**：同一候选人只建一条，跨阶段时更新而非新建
- **常见误报**：候选人主动放缓、岗位暂停招聘。处理方式——`config.yaml` 的 `exclude_jobs` 里排除暂停岗位

## R2 面试后未提交反馈 `interview_feedback_missing`

- **数据**：`list_interview_overview`（面试时间、面试官、反馈状态）
- **条件**：面试结束时间已过 `阈值` 天且 `feedback_status` 为空
- **默认**：2 天
- **严重度**：超过 5 天 → high（会直接影响候选人体验和 offer 时效）
- **反噪音**：按「面试官 + 岗位」聚合，同一面试官积压 ≥3 条时合并成一条「XX 处积压 3 场未反馈」
- **归因提示**：周报里按面试官聚合，这是最容易出「某个人的习惯问题」的地方

## R3 职位长期无新简历 `job_no_resume`

- **数据**：`search_jobs` + 简历投递时间
- **条件**：职位在招且 `今天 - 最后一份简历时间 > 阈值`
- **默认**：7 天
- **严重度**：medium；急聘岗位（`config.urgent_jobs`）默认 3 天
- **反噪音**：每个职位每周最多报一次，且优先放周报而非日报

## R4 群聊催办信号 `chat_nudge_signal`

- **数据**：`messages-search` 关键词命中
- **条件**：命中 `feishu.keyword_watch` 中任一词，且该消息未被后续消息明显闭环
- **默认关键词**：`怎么还没`、`催一下`、`没人回`、`跟一下`、`有进展吗`、`什么时候能好`
- **严重度**：medium；若消息里 @ 了我 → high
- **反噪音**：同一会话同一话题 24 小时内只报一次；命中后往前看 3 条上下文，判断是否已在推进，已在推进的不报
- **常见误报**：讨论流程制度时会用到这些词。判断依据是有没有具体的人和事

## R5 我 @ 了别人但无人回应 `at_me_no_reply`

- **数据**：`messages-search --is-at-me` 反向使用 —— 找我发出的、带 @ 的消息，再看后续有无回应
- **条件**：我发出的消息 @ 了某人，超过 `阈值` 小时该会话内无该人回复，且无其他人代答
- **默认**：24 小时
- **严重度**：medium；若该消息含时间承诺 → high
- **反噪音**：群发通知类 @全体 不纳入；对方休假中（有请假审批记录）不报

## R6 承诺的时间点已过期 `promise_overdue`

- **数据**：我发出的消息中含时间承诺（「明天给你」「周五前发你」「下午同步」）
- **条件**：承诺时间已过，且我未在该会话发出相关交付
- **默认**：过期 4 小时后
- **严重度**：high（这类是最伤信任的漏项）
- **反噪音**：只在我发出的消息里找，不猜测别人的承诺；表述模糊的（「尽快」「这两天」）按 +3 天估算，不计入严格判定
- **注意**：这条最容易误判，建议只在 `strict` 档开启，且判定后必须附带原话引用让用户自行确认

## R7 考勤异常 `attendance_anomaly`

- **数据**：`get_team_attendance`
- **条件**：出现迟到、缺卡、旷工等异常记录
- **默认**：当天即报（不设延迟）
- **严重度**：缺卡 / 旷工 → high；迟到 → low（默认折叠进周报，不进日报）
- **反噪音**：同一人当月同类异常第 3 次起才升级到日报

## R8 审批滞留 `approval_pending`

- **数据**：`get_my_approvals`
- **条件**：待我审批的单据超过 `阈值` 小时未处理；或我发起且被退回
- **默认**：24 小时
- **严重度**：被退回 → high（对方在等）；待我审批 → medium
- **反噪音**：同一单据只报一次

## R9 入职流程停滞 `onboarding_stalled`

- **数据**：`get_onboarding_progress`
- **条件**：待入职人员的某个节点（背调、体检、材料提交）停留超过 `阈值` 天，且距入职日 < 5 天
- **默认**：3 天
- **严重度**：high（入职日前没搞定就是事故）
- **反噪音**：入职日尚远的不报

## 规则设计原则

写新规则时对照这四条，能省掉后面大量调参：

1. **一条规则只回答一个是非问题**。「候选人卡住或面试没反馈」要拆成两条，否则没法单独调阈值
2. **阈值必须有默认值**。用户不知道「几天算久」，先给行业经验值，让他改而不是让他填
3. **必须有反噪音机制**。任何规则上线前先问一句：这条如果每天报，用户几天会烦
4. **必须能回指原始数据**。判定结果里存消息 id 或记录 id，用户点开能自己核对

## 阈值调优记录

每次调阈值都要在 `state/strategy.md` 留一行，格式：

```
2026-11-15 | R2 面试反馈 | 2天 → 3天 | 近2周命中14条，用户实际处理3条，误报率78%
```

半年后回头看这张表，比任何复盘报告都值钱。
